# Требования безопасности Gymshinary

## SR-01. Доступ к пользовательским данным по владельцу

**Требование.** Читать содержимое тренировочной программы, шаблона, сессии и результатов подходов может только их владелец. Изменять эти объекты может только владелец в пределах разрешённых действий; исключение составляет служебное прерывание сессии по SR-02. При создании шаблона его программа, а при запуске сессии выбранный шаблон должны принадлежать тому же пользователю; нельзя связать собственный объект с чужим родительским объектом. Служебный ответ оператору содержит идентификатор запрошенной сессии и её статус. Только для активной сессии он дополнительно содержит отметку последнего сохранённого изменения (либо создания, если изменений ещё не было), чтобы оператор мог оценить, как долго сессия не обновлялась. История тренировочной активности и тренировочное содержимое, включая названия упражнений, веса, повторения и комментарии при их наличии, оператору недоступны. Указание идентификатора чужого объекта не предоставляет доступ к его содержимому или изменению.

**Защитный смысл.** Чужой доступ раскроет сведения о тренировках и физических результатах либо исказит сохранённую историю пользователя.

**Критерий приёмки.** Пользователь B, зная идентификаторы объектов пользователя A, запрашивает его программу, шаблон, сессию и результаты подходов, пытается изменить программу или шаблон A и записать подход в сессию A. Бот не показывает чужие данные и отклоняет изменения; программа, шаблон, состояние сессии и результаты A остаются прежними. Попытка B создать собственный шаблон в программе A или запустить сессию по шаблону A отклоняется: дочерний объект и связь с чужим объектом не создаются, данные обоих пользователей остаются прежними. Пользователь A может выполнить эти действия со своими объектами. При запросе активной сессии A назначенный оператор получает идентификатор, статус и одну отметку последнего сохранённого изменения или создания сессии. После её закрытия ответ содержит только идентификатор и статус. В обоих случаях история тренировочной активности и тренировочное содержимое отсутствуют в ответе.

**ASVS:** [v5.0.0-8.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md#v82-general-authorization-design). Пункт применим к доступу по идентификаторам программ, шаблонов, сессий и результатов: знание идентификатора не заменяет разрешение на конкретный объект. Собственные ограничения служебного доступа оператора заданы текстом требования.

## SR-02. Контролируемое служебное прерывание сессии

**Требование.** Прервать активную сессию через служебную операцию может только назначенный технический оператор, указав непустую причину. Причина из одних пробелов считается отсутствующей. При успешном прерывании система сохраняет прежние результаты подходов и фиксирует, какой оператор прервал какую сессию, когда и по какой причине. Не допускается сохранённое служебное прерывание без соответствующей записи действия, в том числе при сбое во время операции. Знание идентификатора сессии не предоставляет служебных полномочий.

**Защитный смысл.** Несанкционированное прерывание лишит пользователя возможности продолжить тренировку. Без записи об операторе, времени и причине невозможно проверить обоснованность служебного вмешательства.

**Критерий приёмки.** Обычный пользователь B, зная идентификатор активной сессии пользователя A, пытается выполнить служебное прерывание: действие отклоняется, статус и записанные подходы не меняются. Назначенный оператор пытается прервать эту сессию без причины или с причиной из одних пробелов: действие также отклоняется, статус и подходы остаются прежними. При прерывании тем же оператором с указанной причиной сессия получает статус `прервана`, ранее записанные подходы остаются прежними, а запись служебного действия содержит идентификаторы оператора и сессии, время и причину. Попытка оператора с непустой причиной прервать уже завершённую или прерванную сессию отклоняется: статус, результаты и прежняя запись служебного действия не меняются, новая запись успешного прерывания не создаётся. При искусственном сбое сохранения записи служебного действия не остаётся сессии, прерванной этой операцией без такой записи; прежние подходы сохраняются.

## SR-03. Сохранность результатов закрытой сессии

**Требование.** Новые результаты подходов можно добавлять только пока сессия находится в состоянии `активна`. После завершения или прерывания сессии добавление подходов в неё запрещено, а ранее записанные результаты сохраняются. Ограничение действует и при одновременной обработке записи подхода и закрытия сессии: подход не должен сохраняться после уже сохранённого перехода сессии в закрытое состояние. Ограничение доступа к сессии по владельцу задано в SR-01.

**Защитный смысл.** Запись после закрытия исказит историю фактически выполненной тренировки. Для завершённой сессии это также исказит предыдущий результат, который бот показывает в следующих занятиях.

**Критерий приёмки.** После завершения или прерывания собственной сессии её владелец повторно отправляет команду либо нажимает старую кнопку для записи подхода. Бот отклоняет действие; статус, количество подходов, веса и повторения остаются прежними. При одновременной обработке закрытия и записи подхода, если переход в закрытое состояние уже сохранён, новая запись не сохраняется. Пока собственная сессия активна, допустимый подход в неё записывается.

## SR-04. Независимость сессий и истории от редактирования шаблона

**Требование.** При запуске сессии система сохраняет снимок структуры выбранного шаблона. Последующее редактирование программы или шаблона не изменяет этот снимок, состояние сессии и уже записанные результаты. Ограничение относится к активным, завершённым и прерванным сессиям. Изменённый шаблон используется для новых сессий.

**Защитный смысл.** Независимость снимка защищает целостность и достоверность зафиксированной истории: редактирование исходного плана не должно задним числом подменять упражнения и условия, к которым относятся сохранённые результаты. Для прерванной сессии это также сохраняет тренировочный контекст служебного вмешательства, зафиксированного по SR-02, и позволяет разбирать его причины без ретроактивного искажения истории.

**Критерий приёмки.** Пользователь A запускает сессию по шаблону и записывает подход. Затем он изменяет состав упражнений и плановое количество подходов в исходном шаблоне. Снимок активной сессии, её состояние и записанный результат остаются прежними. Аналогичное редактирование не меняет снимки и результаты завершённых и прерванных сессий. Новая сессия, запущенная после допустимого закрытия активной, содержит обновлённый план.

## SR-05. Достоверная идентификация пользователя

**Требование.** В текущей архитектуре обновления принимаются только в ответ на исходящие запросы приложения к Telegram Bot API по HTTPS с проверкой подлинности сервера. Приложение не предоставляет входящий HTTP-интерфейс для приёма Telegram-обновлений. Система определяет автора действия исключительно по системному полю `from.id` сообщения или нажатия кнопки из доверенного обновления. Идентификатор пользователя, имя и роль из текста команды или данных кнопки не могут подменить автора или предоставить операторские полномочия. Новые программы и шаблоны создаются от имени установленного автора. Если отправителя невозможно определить, доступ к личным данным и изменяющие операции отклоняются.

**Защитный смысл.** Подмена личности позволяет обойти проверку владельца данных или выдать себя за технического оператора. Проверка прав должна опираться на установленного отправителя, а не на сведения, которые пользователь указал самостоятельно.

**Критерий приёмки.** Проверка маршрутов развёрнутого приложения подтверждает отсутствие доступного HTTP-интерфейса для приёма Telegram-обновлений. Отдельно в обработчик передаются доверенные тестовые обновления с `from.id` пользователя B: одно с ID пользователя A в тексте команды, другое с ID назначенного оператора в данных нажатия кнопки. Автором обоих действий определяется B. Программа от имени A не создаётся, действие с операторскими полномочиями отклоняется, чужие данные и серверный список операторов не меняются. Доверенное обновление без определяемого отправителя не раскрывает личные данные и не изменяет состояние; корректное обновление от A позволяет создать собственную программу. Проверка конфигурации клиента подтверждает, что он обращается к Telegram Bot API по HTTPS и проверка сертификата не отключена.

## SR-06. Защита токена Telegram-бота и секретов подключения

**Требование.** Действующий токен Telegram-бота и пароль подключения к PostgreSQL передаются приложению вне исходного кода и Git и не включаются в публикуемые сборочные артефакты. В локальной разработке допускается `dotnet user-secrets`, который хранит значения вне каталога проекта, но не шифрует их и не является хранилищем секретов для развёртывания. В среде развёртывания секреты передаются через конфигурацию этой среды, а доступ к ним ограничивается её средствами: правами учётных записей, файлов, контейнера или хранилища секретов. Доступ предоставляется процессу приложения и уполномоченным лицам. Команды бота не позволяют прочитать или изменить секреты; они не выводятся в ответы, технические журналы и сообщения об ошибках. Замена секрета в конфигурации и перезапуск приложения должны переводить приложение на новое значение без изменения исходников и пересборки; прежнее значение больше не используется приложением. Отзыв токена и его проверка на стороне Telegram находятся за границей ответственности Gymshinary.

**Защитный смысл.** Утечка токена позволяет управлять ботом от имени сервиса, а утечка пароля БД — получить доступ к тренировочным данным. Удаление секрета только из последней версии файла не устраняет его раскрытие в истории репозитория.

**Критерий приёмки.** Проверка отслеживаемых файлов, истории репозитория и публикуемых артефактов не обнаруживает действующих секретов. В локальной разработке тестовые значения загружаются из User Secrets; в выбранной среде развёртывания — из её конфигурации. Учётная запись без предоставленных прав не может прочитать секреты этой среды; пользовательские команды не возвращают и не меняют их. При искусственных ошибках Telegram API и подключения к БД тестовые секреты отсутствуют в ответах и журналах. В изолированном тестовом окружении значения токена и пароля заменяются в конфигурации, приложение перезапускается без изменения исходников и пересборки. Тестовый адаптер внешнего API и тестовая БД подтверждают использование новых значений; попыток приложения использовать прежние значения после перезапуска нет. Проверка того, принимает ли Telegram ранее отозванный токен, в критерий не входит.

## SR-07. Целостность данных при сохранении и сбоях

**Требование.** Атомарно сохраняются изменения одной отдельной изменяющей команды пользователя: например, создание программы, создание шаблона или добавление одного упражнения со всеми его параметрами и связью с шаблоном. В пределах такой команды либо сохраняются все предусмотренные изменения, либо ни одно из них; частичный объект или связь с несуществующим родительским объектом не остаются. Последовательные команды создания программы, шаблона и упражнений являются самостоятельными операциями; единая транзакция между сообщениями пользователя не требуется. Сбой текущей команды не должен отменять или повреждать данные, сохранённые предыдущими успешными командами, при исправном хранилище и в рамках его гарантий транзакций. Сообщение об успехе отправляется после подтверждения сохранения хранилищем. При ошибке, если исход сохранения установить нельзя, система сообщает об отсутствии подтверждения, а не утверждает успех или откат. Восстановление после физической потери хранилища регулируется SR-09.

**Защитный смысл.** Частичное сохранение или преждевременное подтверждение создают недостоверный план и могут привести к незаметной потере пользовательских данных. Согласованность требуется для всех связанных тренировочных объектов, а не только для состояния сессии.

**Критерий приёмки.** Пользователь A отдельными командами создаёт программу, шаблон и первое упражнение; каждое сохранение подтверждено. При добавлении второго упражнения искусственно вызывается ошибка между сохранением его параметров и связи с шаблоном, до фиксации операции. Изменения текущей команды откатываются: второе упражнение и частичная связь отсутствуют, программа, шаблон и первое упражнение остаются прежними; сообщение об успехе не отправлено. При успешном повторе второе упражнение сохраняется со всеми параметрами и корректной связью, после перезапуска приложения оба упражнения доступны. Если в отдельной проверке подтверждение сохранения недоступно, ответ сообщает, что результат не подтверждён, и не выдаёт неизвестный исход за успешное сохранение или гарантированный откат.

## SR-08. Защита хранилища от внедрения команд через ввод

**Требование.** Названия программ, шаблонов и упражнений, причины служебного прерывания и другие переданные пользователем значения должны обрабатываться как данные и не могут изменять структуру или назначение запросов к PostgreSQL. Содержимое этих значений не должно приводить к выполнению произвольных команд хранилища, обходу ограничения по владельцу, чтению или изменению посторонних записей. Недопустимый для поля ввод отклоняется без изменения данных.

**Защитный смысл.** Если пользовательский текст становится частью исполняемого запроса, злоумышленник может получить чужие данные, изменить или удалить записи в обход прикладных проверок доступа.

**Критерий приёмки.** В изолированной тестовой PostgreSQL пользователи A и B имеют собственные программы. B выполняет доступные ему операции с названиями, содержащими апостроф и тестовые SQL-фрагменты, например `' OR '1'='1` и `'; DROP TABLE <имя_тестовой_таблицы>; --`. Тестовые значения адаптируются к фактической схеме и проверяемому запросу. По трассировке запросов на тестовых данных проверяется, что внедрённый фрагмент передаётся только как значение или отклоняется до отправки запроса и не выполняется как SQL. Чужие записи не возвращаются, программа A и структура БД остаются прежними. Аналогичный ввод в причине разрешённого служебного действия не вызывает дополнительных изменений хранилища. Обычное название с апострофом сохраняется как текст.

## SR-09. Восстановление данных из защищённых резервных копий

**Требование.** Для PostgreSQL должна быть предусмотрена воспроизводимая процедура создания согласованной резервной копии и восстановления из неё программ, шаблонов, сессий, результатов и записей служебных действий с сохранением владельцев и связей. Для текущей локальной среды копия создаётся уполномоченным участником перед миграцией или другим действием, способным изменить либо удалить сохраняемые данные. Календарное расписание для выключенной локальной среды не требуется. При появлении постоянно работающей среды эксплуатации до её ввода должны быть определены ответственный за копирование, расписание и допустимая потеря данных между копиями. Читать, изменять и удалять копии могут только уполномоченные лица и процессы; обычные пользователи бота не получают к ним доступ. Копии не размещаются в публичном репозитории и общедоступных каталогах.

**Защитный смысл.** Потеря или повреждение БД уничтожает историю тренировок и след служебного вмешательства. Незащищённая резервная копия раскрывает те же данные, что и основное хранилище.

**Критерий приёмки.** Уполномоченный участник по документированной процедуре создаёт копию тестовой БД перед изменением схемы или удалением данных. Копия восстанавливается в отдельную пустую БД: программы, шаблоны, сессии, результаты и служебные записи доступны, их значения, владельцы, состояния и связи совпадают с зафиксированным состоянием на момент копирования. Проверка от имени учётной записи без соответствующих прав не позволяет прочитать, подменить или удалить копию; через команды бота получить её также невозможно, копия отсутствует среди отслеживаемых Git файлов. При подготовке постоянно работающей среды отдельно проверяется наличие ответственного, расписания, допустимого объёма потери данных и успешное выполнение копирования по этому расписанию; для текущего локального запуска эта условная проверка не требуется.

## SR-10. Конфиденциальность технических журналов и сообщений об ошибках

**Требование.** Технические журналы не должны содержать полные тексты пользовательских сообщений, названия личных программ, веса, повторения и причины служебного прерывания. Для диагностики допускаются время, тип операции, технические идентификаторы и код ошибки. Доступ к техническим журналам предоставляется только уполномоченным участникам сопровождения и процессам диагностики в пределах необходимых полномочий. Ответ об ошибке не должен раскрывать внутренний стек вызовов, запросы к БД или сведения о чужих объектах. Обязательная запись служебного действия по SR-02 хранится с предусмотренным доступом и не копируется целиком в общие технические журналы. Защита секретов во всех диагностических каналах определяется SR-06.

**Защитный смысл.** Личные тренировочные данные могут утечь через журналы и диагностические ответы даже при правильной проверке прав в основных сценариях. Избыточная диагностика также раскрывает внутреннее устройство приложения.

**Критерий приёмки.** В тестовой среде пользователь создаёт программу с уникальным контрольным названием и записывает подход с известными весом и повторениями; оператор выполняет разрешённое прерывание с контрольной причиной. Затем искусственно вызываются ошибка хранилища и отказ доступа к чужому объекту. Уполномоченная учётная запись сопровождения может прочитать технические журналы через настроенный канал диагностики; попытка чтения через этот же канал учётной записью без полномочий отклоняется. В журналах отсутствуют полные входящие сообщения, контрольные строки и содержимое подходов; по разрешённым метаданным можно определить время, тип и исход операций. Пользователь получает понятное сообщение о неудаче без стека вызовов, SQL-запроса и чужих данных. В предназначенной для этого записи служебного действия сохраняются оператор, время и причина согласно SR-02.
